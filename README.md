# near-policy-vault

**Live demo: https://alan021011.github.io/near-policy-vault/** (testnet)

[![tests](https://github.com/Alan021011/near-policy-vault/actions/workflows/tests.yml/badge.svg)](https://github.com/Alan021011/near-policy-vault/actions/workflows/tests.yml)

> **Status: work in progress.** The NFT vault contract, the per-vault EVM address, the spending policy, the proposal queue and **signing from the contract** run on testnet: NFT vaults have spent ETH on Sepolia under their policy, and a pending signature has been cancelled on Sepolia. The **two-phase sale** (M8) closes the two worst threats: a transfer needs a sale window that waits the policy delay (at least 10 minutes) and that the guardian can veto (stolen owner key); a buyer's audit plus `cancel_nonce` detect and neutralise any signature or ERC-20 approval the seller left, and `buy` pays the seller and hands over the NFT in one transaction, only during the sale the buyer audited. The asynchronous flows are also tested in a local NEAR sandbox that anyone can run with one command (M9), where an attack suite tries 42 attacks from the threat model and all are refused (M10); an ERC-20 transfer has been signed by the contract and mined on Sepolia under the token cap.
> Built for the NEAR HACKATHON 2026, track `nfts` (also aiming at `security` and `open` only if they work end to end).

An NFT that **owns an account on another chain** and can only move its funds under a spending policy enforced by a NEAR contract.

## The idea

- Each NFT is a vault. Its EVM address is derived with NEAR Chain Signatures from the contract account and the path `vault-<token_id>`.
- The contract only asks the network to sign a transaction if it satisfies the vault's policy: daily cap, allowed destinations, a delay with cancel, a guardian veto, and no unlimited token approvals.
- The contract **computes the signing hash itself** from fields it has validated. It never signs a hash supplied by a caller.
- Selling the NFT hands over the vault without handing over any private key. The sale runs in two phases so a seller cannot keep a pre-signed transaction (see `docs/THREAT_MODEL.md`, threat 1).

## How to verify (will be filled in as pieces land)

Each step follows the pattern "run X, expect Y". Nothing is claimed until it has been run.

1. Regenerate the reference vectors with viem:
   `cd scripts && npm ci && node gen-vectors.mjs`
   Expect: `wrote 19 vectors to .../vectors/eip1559_signing_hash.tsv` and `git status` shows no change (the committed vectors are reproduced exactly). `npm ci` installs the exact versions in `package-lock.json`.
2. Run the Rust tests:
   `cd contract && cargo test`
   Expect: 191 unit tests (13 EVM helpers, 14 policy, 164 contract) and `rust_signing_hash_matches_viem` pass. If you change one character in a vector, that test fails with the case name.
   On Windows, `contract/.cargo/config.toml` sets `AWS_LC_SYS_PREBUILT_NASM=1` so NASM is not needed.
3. Run the asynchronous flows in a local NEAR sandbox (M9; Linux or macOS, WSL on Windows; needs `cargo-near`; no testnet account, no Sepolia ETH, about 2 minutes after the first build):
   `cd sandbox-tests && ./build-wasm.sh && cargo test -- --test-threads=4`
   Expect: 8 tests pass (`test result: ok. 8 passed`). They deploy the contract wasm built from this source (on the author's machine it is byte-identical to the testnet deployment, `27e7b8ae…`; a build on another machine differs in bytes until the reproducible Docker build lands), a mock Chain Signatures contract that answers with the same shapes (and can hold its answer with yield/resume like the MPC network, sign with the wrong key, answer garbage or fail) and the `transfer_call` test receiver, then run mint, signing, signature in flight, bad signer answers, signer timeout, guardian veto, sale and `buy`, the `transfer_call` attack and `cancel_nonce` with real cross-contract promises; the sandbox clock is moved with `fast_forward`. Details in `sandbox-tests/README.md`. The same tests run on every push in GitHub Actions (`.github/workflows/tests.yml`).
   The same command also runs the **attack suite** (`tests/attacks.rs`). To see its table: `cargo test --test attacks -- --nocapture` (or `npm run attack` in `scripts/`). Expect one `BLOCKED [threat] attack` line per attack and `42/42 attacks blocked`.

## Known limits

See `docs/THREAT_MODEL.md`. Residual risks that this design does not remove: trust in the MPC network, and whoever controls the contract's upgrade keys.

- **Upgrade key (threat 9).** Today the contract account keeps a full-access key, so its owner can replace the code (this is how `migrate` was deployed). Before the final submission the plan is to delete that key so the code can no longer change, and to show it here with `near account view-account-summary` ("0 full access keys"). Until then, treat the contract as upgradable by its deployer.
- **Stolen owner key (threat 16).** A transfer needs a sale window that waits max(policy delay, 10 minutes) and that the guardian can veto, so a thief holding the owner's key has to get past the guardian, and an owner who still holds the key can cancel the thief's sale during that wait. What remains: a thief can replace the guardian after max(2 x delay, 3 days) (threat 18), during which the guardian can keep vetoing; and an owner who notices nothing in 10 minutes cannot react.
- **The buyer must run the audit.** The contract cannot read Ethereum, so it cannot tell whether every nonce it signed is already mined, or whether an ERC-20 approval it signed still has an allowance. `scripts/sale-audit.mjs` does both checks (it uses public RPCs by default; a careful buyer uses their own node or compares two). During a sale the vault only signs cancellations, so the state does not change under the audit, and `buy` names the audited sale, so a seller who restarts the sale cannot be paid by an old audit. A sale without a price, paid outside the contract, is only as safe as the escrow that binds it with `memo: "sale:<id>"`; a direct off-chain payment is not protected.
- **Seller payment.** `buy` sends the price to the seller in the same transaction. If the seller's account no longer exists, that transfer fails and the price stays in the contract.
- **`transfer_call` that comes back.** Until the transfer resolves, nobody can act as the vault's owner (the lock lapses after 1 hour if the resolution never runs). If the receiver returns the NFT, the transfer has already ended the seller's sale and deleted their policy; the seller gets the vault back locked and must set a policy and start a new sale.
- **Sale windows close.** A window stays open 24 hours after it opens; after that a new sale must be started (an old sale never leaves the vault transferable).
- **A delay of 0 disables the guardian's veto on spending.** With `delay_ms` = 0 a proposal can be signed in the same block, so the guardian never gets a chance to veto it (it still protects its own replacement, which waits at least 3 days).
- **Uncertain nonces survive a sale.** The list of nonces with an unknown outcome (`get_uncertain`) stays with the vault, so a buyer sees it and can cancel them; the queue and the policy do not survive.
- **One chain per vault.** The nonce counter belongs to the chain of the first signature, so a vault cannot move to another EVM chain afterwards (its address exists on every chain, but this contract only signs for that one).
- **Daily windows.** Caps use fixed 24-hour windows and are charged when a transaction is signed, so up to twice a cap can be signed across a window boundary.
- **Guardian trade-off.** The guardian can veto spending and loosening, but not its own replacement, which waits max(2 x delay, 3 days). This keeps a lost or hostile guardian from freezing the vault; the price is that a thief holding the owner's key can remove the guardian after that wait.
- **Gas on current Sepolia.** Sending ETH to an address that has never been used costs about 207,000 gas there (about 12,000 to an existing one), so a vault that pays new addresses needs a `max_gas_cost` with room for that. With too little gas such a transfer is mined but reverted (the nonce is used, the value is not sent). The same holds for an ERC-20 `approve` that creates a new allowance: about 129,000 gas there (about 20,000 to set one back to 0); a first live run with 60,000 was mined and reverted. `buy-testnet-check.mjs` estimates the gas from the vault's address.
- **Uncertain outcomes cost cap room.** When the signer fails, the charge is kept (a signature might exist), so the day's cap shrinks until the window resets; an identical retry is not charged again.
- **History marker.** A cancellation is stored with `proposal_id` = 2^64-1 (`CANCEL_PROPOSAL_ID`), so old records keep their format.
- **`ecrecover`.** It needs near-sdk's `unstable` feature; the host function itself is part of the NEAR runtime.
- **Signer contract.** The Chain Signatures contract is fixed at init (`signer_id`). Whoever deploys chooses it, and changing it needs a code upgrade (threat 9).
- **Token ids are never reused.** Each vault's EVM account depends only on its id. There is no burn; adding one must never reissue an id, or two owners would share one account.
- **Library event gap.** `near-contract-standards` 5.30.0 emits `nft_transfer` without `authorized_id` when an approved account transfers. This contract also emits `vault_transfer` (standard `policy_vault`) with that field and keeps the last transfer on-chain (`vault_transfer_info`).
- **Approval deposits.** The library keeps the storage deposit of approvals cleared by a transfer; this contract refunds it to the previous owner.
