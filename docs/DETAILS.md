# near-policy-vault: full details

This page keeps everything the README summarises: what each piece does and how it was tested live, all 18 verification steps, how to set up the guardian alerts, and every known limit. Nothing here is newer than the README; the README links to each section.

## The idea

- Each NFT is a vault. Its EVM address is derived with NEAR Chain Signatures from the contract account and the path `vault-<token_id>`.
- The contract only asks the network to sign a transaction if it satisfies the vault's policy: daily cap, allowed destinations, a delay with cancel, a guardian veto, and no unlimited token approvals.
- The contract **computes the signing hash itself** from fields it has validated. It never signs a hash supplied by a caller.
- Selling the NFT hands over the vault without handing over any private key. The sale runs in two phases so a seller cannot keep a pre-signed transaction (see `docs/THREAT_MODEL.md`, threat 1).

| Proposal queue (M6) | `propose` checks the policy; the transaction waits the delay (and any longer delay set later); the owner cancels or the guardian vetoes; at most 8 queued. | Signing from the contract (M7) | `execute_proposal` (the owner, or since agent mode the policy's agent; after the delay) charges the caps, takes the next nonce and asks `v1.signer-prod.testnet` to sign the hash it computed; the vault is locked meanwhile (no second signature, no transfer). The private callback reads the signer's answer by hand (it never panics), **recovers the signer with `ecrecover` and requires the vault's own key**, then stores the raw signed transaction (`get_signed`, `get_signed_versions`, `list_signed`). An answer that recovers to another key is undone (caps, nonce, queue). If the signer fails, answers something unreadable or uses a format the contract does not expect, a valid signature might still exist, so the outcome is *uncertain*: the nonce stays used, the charge stays, and the proposal returns pinned to that nonce, so a retry yields the identical transaction and is not charged twice. `cancel_nonce` signs a 0-value self-transfer with an already used nonce, which makes anything else signed with it unminable once that cancellation is mined; `execute_proposal(.., replace_nonce)` re-signs a stuck nonce. ## Try the guardian alerts yourself

A guardian can only stop a payment it knows about. Two ways to be told:

**In the browser (no setup).** Open the [web page](https://alan021011.github.io/near-policy-vault/), connect the NEAR testnet wallet that is a vault's guardian, and in "Vaults I guard" press **Watch my vaults**. While that tab stays open, the browser shows a notification whenever one of those vaults has a payment waiting; clicking it opens the vault with its red "Stop this payment" button.

**On your phone, with Telegram** (`scripts/guardian-alerts.mjs`, Node 18+, no npm packages):
1. In Telegram, open **@BotFather**, send `/newbot`, choose a name and a username ending in `bot`, and copy the token it gives you. Keep it private.
2. Store the token in an environment variable, never in a file of the repository. PowerShell: `[Environment]::SetEnvironmentVariable('TELEGRAM_BOT_TOKEN', '<token>', 'User')` (then open a new terminal); bash: `export TELEGRAM_BOT_TOKEN=<token>`.
3. Open your bot in Telegram and press **Start** (a bot cannot write first).
4. `cd scripts && node guardian-alerts.mjs m3.alan-vault-2026.testnet --guardian <your-account>.testnet --test`
   Expect: the list of chats that wrote to the bot, each with its `TELEGRAM_CHAT_ID`. Store yours like the token (PowerShell: `[Environment]::SetEnvironmentVariable('TELEGRAM_CHAT_ID', '<id>', 'User')`). Alerts go only to that chat: anyone else who finds the bot gets nothing. Run `--test` again: expect "test message sent", and the message in Telegram.
5. Run it without `--test` and leave it running. Expect a "Watching N vault(s)" message, then an alert, with its warning signs and a link to the vault, each time one of your vaults has a payment, a looser rule change or a handover waiting.

The script only reads the contract: it holds no NEAR key and cannot sign or veto. You stop a payment yourself, with your wallet, from the link. Alerts arrive only while the script (or the browser tab) is running; a hosted service with one shared bot, where a guardian links their Telegram by signing with their NEAR wallet, is future work.

## Known limits

See `docs/THREAT_MODEL.md`. Residual risks that this design does not remove: trust in the MPC network. The contract itself can no longer be changed (its account has no keys); `docs/MIGRATION.md` says what happens if a bug is found, and [`docs/V2.md`](../docs/V2.md) says how a next contract would remove the limits below that come from the contract (rolling window, spending that survives a handover, one key per vault, an agent always paired with a guardian, unique invoice references, a fee floor for the agent, several chains), with the invariant and the tests each change would need. V2 is a design only: nothing of it is deployed.

- **No independent audit.** The contract has not been audited by a security firm. The reviews in this README were done by another AI model; the tests and attack suite cover the threats listed in the threat model, not every possible bug.

- **The contract is final (threat 9).** On 2026-11-10 the contract account's only full-access key was deleted (transaction `AgJL65MQNxGK58Ai1Forvh71YD3HwpiqLMPUL61TwvMd`); `view-account-summary` shows "Account is locked (no access keys)". Nobody can change the code any more, so a bug cannot be fixed in place: a fix would be a new contract at a new account, and vaults would stay where they are. The deployed code is the reproducible build of step 4. `migrate` and `migrate_policies` can no longer be called (they were private to the contract account).
- **Stolen owner key (threat 16).** A transfer needs a sale window that waits max(policy delay, 10 minutes) and that the guardian can veto, so a thief holding the owner's key has to get past the guardian, and an owner who still holds the key can cancel the thief's sale during that wait. What remains: a thief can replace the guardian after max(2 x delay, 3 days) (threat 18), during which the guardian can keep vetoing; and an owner who notices nothing in 10 minutes cannot react.
- **The buyer must run the audit.** The contract cannot read Ethereum, so it cannot tell whether every nonce it signed is already mined, or whether an ERC-20 approval it signed still has an allowance. `scripts/sale-audit.mjs` does both checks (it uses public RPCs by default; a careful buyer uses their own node or compares two). **The audit fails closed:** if a required check cannot be completed (for example a public node answers "pruned history unavailable" to the search for Approval events), the web page says "Check incomplete" and keeps taking over disabled, and the script says INCOMPLETE with exit code 2; a handover that has not opened yet is shown as "Not open yet", never as safe. Approval events are read from nodes that keep old blocks (Tenderly, then publicnode). Before this fix, found by an external AI review, a failed event search was only a warning. During a sale the vault only signs cancellations, so the state does not change under the audit, and `buy` names the audited sale, so a seller who restarts the sale cannot be paid by an old audit. A sale without a price, paid outside the contract, is only as safe as the escrow that binds it with `memo: "sale:<id>"`; a direct off-chain payment is not protected.
- **Seller payment.** `buy` sends the price to the seller in the same transaction. If the seller's account no longer exists, that transfer fails and the price stays in the contract.
- **`transfer_call` that comes back.** Until the transfer resolves, nobody can act as the vault's owner (the lock lapses after 1 hour if the resolution never runs). If the receiver returns the NFT, the transfer has already ended the seller's sale and deleted their policy; the seller gets the vault back locked and must set a policy and start a new sale.
- **Sale windows close.** A window stays open 24 hours after it opens; after that a new sale must be started (an old sale never leaves the vault transferable).
- **A delay of 0 disables the guardian's veto on spending.** With `delay_ms` = 0 a proposal can be signed in the same block, so the guardian never gets a chance to veto it (it still protects its own replacement, which waits at least 3 days).
- **Uncertain nonces survive a sale.** The list of nonces with an unknown outcome (`get_uncertain`) stays with the vault, so a buyer sees it and can cancel them; the queue and the policy do not survive.
- **One chain per vault.** The nonce counter belongs to the chain of the first signature, so a vault cannot move to another EVM chain afterwards (its address exists on every chain, but this contract only signs for that one).
- **Without a guardian, caps do not survive a sale (M12, R12-4).** An owner (or a thief with the key) can start a sale, wait the 10-minute minimum and transfer the vault to another account of theirs; the new owner starts with fresh daily caps. With a guardian, it can veto that sale. The web page marks vaults without a guardian.
- **An allowed spender is trusted with up to the token's daily cap per day.** Approvals count against the cap (M12, R12-3), but whatever is approved can be pulled with `transferFrom` until revoked.
- **Deploy and initialise together (M12, R12-10).** `new` has no caller check; deploying and calling `new` in two transactions would let someone else choose the signer first. Use one transaction (deploy with init call).
- **Small amounts can stay in the contract (M12, R12-11).** There is no withdraw: a signer deposit above 1 yoctoNEAR that the signer does not use, or the price of a sale whose seller account no longer exists, stays in the contract.
- **A purchase memo must start with `sale:` (M12, R12-13).** A memo such as `buy sale:3` does not bind the transfer to a sale.
- **The signer is trusted to give each vault its own key (M12, R12-14; threat 8).** The contract does not check that two vaults received different keys.
- **The audit reads Ethereum near the latest block (M12, R12-7).** It pins one block, two behind the head, and reads every Ethereum value at that block, so a load-balanced public node cannot mix states from different servers; if the node's newest block is more than 5 minutes old, the audit is incomplete, never safe. A reorg deeper than that could in theory bring back a signature that looked replaced; it re-reads the sale at the end and fails if it changed.
- **Signing needs at least 100 Tgas (M12, R12-12)**, so the signer call cannot run out of gas and leave an uncertain outcome.
- **Daily windows.** Caps use fixed 24-hour windows and are charged when a transaction is signed, so up to twice a cap can be signed across a window boundary.
- **Guardian trade-off.** The guardian can veto spending and loosening, but not its own replacement, which waits max(2 x delay, 3 days). This keeps a lost or hostile guardian from freezing the vault; the price is that a thief holding the owner's key can remove the guardian after that wait.
- **Gas on current Sepolia.** Sending ETH to an address that has never been used costs about 207,000 gas there (about 12,000 to an existing one), so a vault that pays new addresses needs a `max_gas_cost` with room for that. With too little gas such a transfer is mined but reverted (the nonce is used, the value is not sent). The same holds for an ERC-20 `approve` that creates a new allowance: about 129,000 gas there (about 20,000 to set one back to 0); a first live run with 60,000 was mined and reverted. `buy-testnet-check.mjs` estimates the gas from the vault's address.
- **Agent mode (threats 24-28).** Within the policy, an agent can still spend up to the caps on approved recipients; only the waiting time and the guardian stand in the way, so a vault with an agent should have both. The agent can sign any ready proposal in the queue, the owner's too. It can also sign a payment with a fee too low to be mined (M21, R21-2), which blocks later payments until the owner signs `cancel_nonce`; the owner removes the agent at once, since removing it is a tightening. The quality of the agent's own decisions is out of scope: the contract assumes it can be wrong.
- **Warning signs are simple and advisory (M35).** They are computed off-chain by the page, the watcher or the agent, from the vault's last 20 signed payments and its waiting ones; the contract never sees them. They are plain rules, not a fraud model: a monthly bill to the same recipient is flagged as a possible duplicate (a false alarm the guardian dismisses), a look-alike address that differs in its first or last 4 characters is not caught, and the wording checks are English keyword patterns that a careful attacker can avoid. Only the agent and the Try page have the invoice text; for payments already queued, the page and the alert judge the transaction alone.
- **The drawn card is informational.** It is computed from the contract's own state when read; some wallets or marketplaces do not display SVG `data:` images, and the card cannot show Ethereum balances (the contract cannot read Ethereum). Enumeration pages return at most 100 tokens.
- **The guardian must be watching.** A veto works only within the waiting time. `scripts/guardian-alerts.mjs` sends Telegram alerts while it runs on the guardian's machine; a hosted push service is future work. Choose a waiting time long enough for your guardian to react (hours rather than seconds for a person).
- **A price or a reserved buyer binds only `buy` (external review, round 3).** During an open handover window, the owner or an account they approved with `nft_approve` can still move the NFT with `nft_transfer` or `nft_transfer_call`, without paying the price and past the reservation. A buyer never pays without receiving (`buy` pays and transfers in one step); the risk is for a seller who approved a marketplace that ignores the price. The web page warns about it: the Safety check and the Handover section list every account approved to move the NFT (red while a priced handover is open), and the owner can revoke them all with one button (`nft_revoke_all`). `docs/V2.md` item 13.
- **The `transfer_call` lock lapses after one hour (external review, round 3).** If the resolution of an `nft_transfer_call` took more than an hour, the receiver could act as owner before it resolves, and the late callback removes the lock without checking it is its own. NEAR resolves callbacks within blocks in practice, and the receiver still needs its own handover window (10 minutes) to move the vault again. `docs/V2.md` item 14.
- **Removing the agent does not stop a signature already in progress (external review, round 3).** A rule change applies to what is signed next; a payment the agent already sent to the signer, authorised under the rules in force then, can still be signed and broadcast. The owner then cancels that nonce (`cancel_nonce`). `docs/V2.md` item 15.
- **Revoking a token permission needs the token and the spender still allowed (external review, round 3).** `approve(spender, 0)` passes through the same policy check as any approval, so remove the token or the spender from the rules only after revoking. `docs/V2.md` item 16.
- **A cancellation needs room under the daily cap.** `cancel_nonce` signs a 0-value transaction whose worst-case gas is charged against the ETH daily cap, like any payment, so it cannot be used to burn the vault's ETH in fees. The price: if the day's cap is used up (for example by an agent that also left a nonce stuck with a fee too low, R21-2), the owner cannot cancel that nonce until the 24-hour window resets, and the vault pays nothing meanwhile. No funds are lost; the owner removes the agent at once (a tightening) and cancels after the reset. Found by an external AI review; `docs/V2.md` proposes a small separate allowance for cancellations.
- **Uncertain outcomes cost cap room.** When the signer fails, the charge is kept (a signature might exist), so the day's cap shrinks until the window resets; an identical retry is not charged again.
- **History marker.** A cancellation is stored with `proposal_id` = 2^64-1 (`CANCEL_PROPOSAL_ID`), so old records keep their format.
- **`ecrecover`.** It needs near-sdk's `unstable` feature; the host function itself is part of the NEAR runtime.
- **Signer contract.** The Chain Signatures contract is fixed at init (`signer_id`). Whoever deploys chooses it, and it can no longer change, since the contract is locked (threat 9).
- **Token ids are never reused.** Each vault's EVM account depends only on its id. There is no burn; adding one must never reissue an id, or two owners would share one account.
- **Library event gap.** `near-contract-standards` 5.30.0 emits `nft_transfer` without `authorized_id` when an approved account transfers. This contract also emits `vault_transfer` (standard `policy_vault`) with that field and keeps the last transfer on-chain (`vault_transfer_info`).
- **Approval deposits.** The library keeps the storage deposit of approvals cleared by a transfer; this contract refunds it to the previous owner.
